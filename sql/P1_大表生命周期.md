## 0. 目标表（只追加日志/流水）

| 表 | 特征 | 保留建议 |
| --- | --- | --- |
| tx_payment_logs | 支付渠道通信日志（含 request/response） | 3 个月冷归档，6 个月清理 |
| tx_order_logs | 订单操作日志 | 6 个月冷归档，12 个月清理 |
| sys_operation_logs | B 端操作审计 | 12 个月冷归档，长期审计另存 |
| sp_inventory_logs | 库存流水（对账审计） | 6 个月冷归档，12 个月清理 |
| tx_delivery_traces | 物流轨迹（量大） | 3 个月冷归档，6 个月清理 |
| mkt_promotion_usage_logs | 促销使用记录 | 12 个月冷归档 |

> 除上表外，`usr_login_histories` / `sys_login_histories` 也可按同策略（PG 侧已分区）。

## 1. PostgreSQL（已落地）

`pgsql/03_partitions.sql` 已按月 RANGE 分区：`usr_login_histories`、`sys_login_histories`、`sys_operation_logs`、`tx_order_logs`、`tx_payment_logs`、`sp_inventory_logs`。
- 表 DDL 以 `PARTITION BY RANGE (created_at)` 定义，`00_drop_tables.sql` 清理，`create_monthly_partitions('表名','2026-07-01',3)` 预建分区；
- 生产建议用 pg_partman 自动滚动；冷数据直接 DETACH + 转存对象存储，保留 pg_dump/恢复脚本即可。

## 2. MySQL（方案：归档 + 冷库，不在线分区）

MySQL 分区要求分区键纳入所有唯一键（`sp_inventory_logs.uk_ref_type(reference_id_uq, change_type)`、`mkt_promotion_usage_logs` 等会因此被破坏），且在线 DDL 复制成本高，**不建议直接加 RANGE 分区**。采用 **“在线表只留近期 + 按月归档表”** 策略：

### 2.1 归档表（shadow/archive）

```sql
-- 示例：tx_payment_logs_202608 归档表（与主表同结构，created_at 前导）
CREATE TABLE tx_payment_logs_202608 LIKE tx_payment_logs;
-- 迁移冷数据
INSERT INTO tx_payment_logs_202608 SELECT * FROM tx_payment_logs
  WHERE created_at < '2026-08-01';
DELETE FROM tx_payment_logs WHERE created_at < '2026-08-01';
```

### 2.2 调度约定（P2 任务治理落地后由调度执行）

- 每日任务：清理已过期会话购物车（`tx_carts.expired_at`）、过期优惠券/积分；
- 每月任务：把上月及更早的 6 张日志表数据按月归档至 `_YYYYMM` 表，按保留期删除在线表冷数据；
- 归档表命名 `原表_YYYYMM`；查询路径：近期查在线表，历史查归档表或对象存储（由应用层路由）。

## 3. 保留期与恢复

| 阶段 | 动作 |
| --- | --- |
| 在线 | 保留最近 N 个月（按 §0 建议） |
| 冷归档 | 转 `_YYYYMM` 表或对象存储（Parquet/CSV + manifest） |
| 清理 | 超过保留期后 DROP 归档或删除对象，保留备份 |
| 恢复 | 归档对象按 manifest 重新导入 `_YYYYMM` 表；出具恢复演练（P2） |
