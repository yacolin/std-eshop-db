> 更新日期：2026-09-03。

## 1. 幂等键设计（现状复核）

### 1.1 支付创建幂等：`tx_payments.idempotency_key`

- 键生成约定：`pay:{user_id}:{order_no}:{sequence}` 或渠道要求的 traceId；由服务层在发起支付前生成并持久化。
- DDL 复核（双库均有）：
  - MySQL：`UNIQUE KEY uk_idempotency_key (idempotency_key)`、列 `NOT NULL`。
  - PG：`UNIQUE (idempotency_key)`、`NOT NULL`。
- 重放语义：同一 `idempotency_key` 重复“创建支付”请求 → 返回已存在支付单（同单同结果），**不重复调渠道**、不重复记账。
- 幂等范围：**支付单级**（一次下单可以多次尝试支付 = 多张支付单，各自幂等键不同；同一笔“发起支付”动作只允许一张支付单）。

### 1.2 支付回调幂等

- 去重依据：`tx_payments.transaction_id`（渠道交易号）`UNIQUE`（两库均有）。
- 规则：回调按 `order_no + transaction_id` 查单；若 `status=paid` 则视为重复回调直接返回成功响应；写 `tx_payment_logs(action='pay')` 且每笔回调一条。
- 防重放：回调签名验签 + `notify_at`/`channel_response` 更新；重复回调不触发重复加库存流水/改订单。

### 1.3 退款申请幂等：`tx_refunds.idempotency_key`

- 键生成约定：`refund:{order_no}:{after_sale_id}:{apply_no}` 等，服务层生成。
- DDL 复核：MySQL `UNIQUE KEY uk_idempotency_key`、PG `UNIQUE (idempotency_key)`，均 `NOT NULL`。
- 重放语义：同键重复申请 → 返回已存在退款单；不重复扣减可退余额、不重复调渠道。

### 1.4 退款回调幂等

- 去重依据：`tx_refunds.channel_refund_id` `UNIQUE`（两库均有）。
- 规则：`status=success` 后重复回调直接幂等返回；同事务联动订单/子单/售后状态（见状态机 §4）。

### 1.5 无单据库存操作幂等（MySQL 特有）

- `sp_inventory_logs.reference_id_uq = NULLIF(reference_id,'')` + `UNIQUE (reference_id_uq, change_type)`（已落实）；PG 日志表按月分区，分区表不建议跨分区 UNIQUE，改为服务层按 `(reference_id, change_type)` 幂等（见 §6 差异说明）。

## 2. 订单—支付—退款一致性口径（计算口径）

对单号 `order_no`：

| 量 | 口径 |
| --- | --- |
| 订单应实付 `payable` | `tx_orders.pay_amount`（父单） |
| 成功支付累计 `paid_sum` | `SUM(tx_payments.amount) WHERE order_no=? AND status='paid'`（或 refunding 中仍计入已收） |
| 成功退款累计 `refunded_sum` | `SUM(tx_refunds.amount) WHERE order_no=? AND status='success'` |
| 可退余额 `refundable` | `paid_sum − refunded_sum`；任何新退款 `amount ≤ refundable` 且 `amount > 0` |
| 订单终态判定 | `refunded_sum ≥ paid_sum` 且 `paid_sum > 0` → 订单/子单可置 `refunded`（防重复：条件更新） |

一致性不变量：
1. `paid_sum > 0 ⇔ tx_orders.payment_status ∈ {paid, refunding, refunded}`；
2. 全退后 `refunded_sum == paid_sum`；
3. `tx_sub_orders.pay_amount 之和 == tx_orders.pay_amount`（无平台级订单拆分场景下）；
4. `tx_order_items.refund_amount ≤ subtotal`，且按 item 累计退费 ≤ 子单退款总额。

## 3. 日对账（reconciliation）检查项与 SQL

见可执行脚本：
- MySQL：`sql/audit/p0_reconcile_audit.sql`
- PG：`pgsql/audit/p0_reconcile_audit.sql`

核心检查（每个脚本输出异常行，返回 0 行 = 通过）：
1. `paid_sum ≠ pay_amount` 且 `payment_status='paid'` 的订单（金额不一致）；
2. `refunded_sum > paid_sum`（超退）；
3. `payment_status='refunded'` 但 `refunded_sum < paid_sum`（状态与金额矛盾）；
4. 存在 `tx_refunds.status='success'` 但父订单/子单/售后状态未联动（状态不同步）；
5. 重复 `channel_response` 外键类矛盾等（按表唯一键复查可交由约束审计）。

## 4. 回调处理的事务边界（服务层）

```
BEGIN;
  -- 1) 条件更新支付单 status: paying/unpaid → paid  (WHERE id=? AND status IN (...))
  -- 2) 若首达：更新 tx_orders.payment_status / status（paid），写 paid_at
  -- 3) 写 tx_payment_logs(action='pay')
  -- 4) 释放/扣减库存：sp_inventory_logs(order_deduct) + 更新 sp_inventories
COMMIT;  -- 任一步失败整体回滚，回调框架负责重试（幂等键/渠道号保证不重复入账）
```

退款回调同构：`tx_refunds.status→success` + `tx_payments` + `tx_sub_orders.refund_status` + `tx_after_sales` + 库存回补（return 类），单事务提交。

## 6. 双库实现差异说明（明确取舍）

| 能力 | MySQL | PG |
| --- | --- | --- |
| 支付/退款幂等唯一键 | 唯一键（同库） | 唯一键（同库） |
| 库存流水幂等 | `reference_id_uq` 生成列 + 唯一键 | 分区表（`PARTITION BY RANGE(created_at)`），跨分区唯一键受限；由服务层按 `(reference_id, change_type)` 幂等 + 唯一业务号兜底 |
| 日志大表 | 未分区（P1 大表生命周期治理项） | 已按月分区（见 `pgsql/03_partitions.sql`） |
| 状态词表 | varchar(20)+注释+服务层守卫 | ENUM 强约束 |

> 以上差异均有文档依据（`SCHEMA_ROADMAP.md` §3 大表生命周期、§0.1 逻辑外键取舍），非遗漏。
