# P0 交易状态机契约（State Machine Contract）

> 依据 `SCHEMA_ROADMAP.md` §2 事项④“订单、支付、退款状态机”交付。
> 本文件定义 `tx_orders` / `tx_sub_orders` / `tx_payments` / `tx_refunds` / `tx_after_sales` 的合法状态集与迁移关系，作为双库（MySQL varchar 注释 / PG ENUM）与服务层的**单一事实来源**。
> 更新日期：2026-09-03。

---

## 0. 本次治理的词汇统一

审计发现 MySQL 与 PG 的支付状态词表不一致：

| 列 | 修复前（MySQL 注释） | PG ENUM | 统一后（双方一致） |
| --- | --- | --- | --- |
| tx_payments.status | pending / processing / success / ... | payment_status: unpaid/paying/paid/failed/refunding/refunded | **unpaid/paying/paid/failed/refunding/refunded** |
| tx_orders.payment_status | unpaid/paying/paid/refunding/refunded | payment_status（含 failed） | **unpaid/paying/paid/failed/refunding/refunded** |

已落地：MySQL `tx_payments.status` 默认值改为 `unpaid`、注释改为统一词表；MySQL seed（`seed_order.py`）写入值由 `success` 改为 `paid`（与 PG seed 一致）；MySQL 与 PG 的 `payment_status` 注释统一含 `failed`。

**约定**：
- “支付状态”用词表 **unpaid/paying/paid/failed/refunding/refunded**。
- “退款单状态”用词表 **pending/processing/success/failed/rejected**（两库一致，不改）。
- PG 侧以 `payment_status` / `refund_status` ENUM 强制；MySQL 侧由注释 + 服务层守卫保证（varchar 不强约束）。
- **订单级 `tx_orders.payment_status` 虽与 `tx_payments.status` 共用同一词表（PG 为同一 ENUM），业务上订单级不持久化 `failed`**：支付失败时订单停留在 `unpaid` 可重试，`failed` 只出现在支付单（`tx_payments.status`）上。

## 1. 父订单 `tx_orders.status`

状态集（词表）：`pending` 待支付 → `paid` 已支付 → `partial_shipped` 部分发货 → `completed` 已完成；另含 `cancelled` 已取消、`closed` 已关闭、`refunding` 退款中、`refunded` 已退款。

合法迁移表（`from → to`）：

| from | to | 触发 | 说明 |
| --- | --- | --- | --- |
| pending | paid | 支付成功回调（全款/子单全支付） | 同时写 payment_status=paid |
| pending | cancelled | 用户取消 | 仅未支付可取消 |
| pending | closed | 超时关单（定时/回调解约） | 覆盖“支付成功与关单竞争”：回调先到则 closed 失败并回滚 |
| paid | partial_shipped | 任一子单发货 | 由子单状态聚合得出 |
| partial_shipped | partial_shipped | 更多子单发货 | — |
| paid / partial_shipped | completed | 全部子单 delivered | 由子单聚合 |
| paid / partial_shipped / completed | refunding | 任一售后单进入退款 | 见 §5 |
| refunding | refunded | 全部关联退款 success | — |
| any | refunded | 全额退款完成 | 终态之一 |
| completed / cancelled / closed / refunded | — | 终态 | 禁止回迁 |

> 禁止：`paid → pending`；`closed/cancelled` 后任何入账类迁移（除对账冲正流水）；`completed` 前不允许 `refunding → paid`。

---

## 2. 子订单 `tx_sub_orders.status`

状态集：`pending` → `paid` → `shipped` 已发货 → `delivered` 已签收 → `completed`；另有 `cancelled` / `closed` / `refunding` / `refunded`。子单还维护 `refund_status`（none/partial_refunded/refunded）作为退款维度。

| from | to | 触发 |
| --- | --- | --- |
| pending | paid | 本子单应支付成功 |
| pending | cancelled / closed | 取消 / 超时（父单关单联动） |
| paid | shipped | 创建发货单并出库 |
| shipped | delivered | 物流签收 |
| delivered | completed | 确认收货 |
| paid/shipped/delivered | refunding | 子单售后发起退款 |
| refunding | refunded | 退款成功（金额=子单实付） |
| refunded | — | 终态 |

> 迁移守卫：发货必须 `reserved → deduct` 库存流水先落；签收/完成必须由物流状态驱动；`refund_status=partial_refunded` 允许再次退款至累计 = pay_amount。

---

## 3. 支付单 `tx_payments.status`

状态集：`unpaid` → `paying` → `paid` / `failed`；`paid` → `refunding` → `refunded`。

| from | to | 触发 | 说明 |
| --- | --- | --- | --- |
| unpaid | paying | 发起渠道下单 | 写幂等键；`expire_at` 内有效 |
| paying | paid | 渠道异步回调成功 | 幂等：同一 `transaction_id`/`idempotency_key` 重复回调不重复记账 |
| paying | failed | 渠道返回失败 / 超时失败 | 允许从 failed 重新发起（新支付单） |
| unpaid/paying | closed | 超时关单 | 或取消关单；若期间回调到达 → 按竞争规则处理（回调成功优先转为 paid 并解锁订单） |
| paid | refunding | 退款申请通过 | 关联退款单 |
| refunding | refunded | 累计退款金额 = amount | 终态 |

> 超时关单规则：`expire_at` 到期且状态仍为 unpaid/paying 才可关单；关单使用 `UPDATE ... WHERE id=? AND status IN ('unpaid','paying')` 防竞争；回调成功应 `UPDATE ... WHERE id=? AND status IN ('paying','unpaid')` 后追加 `tx_payment_logs(action='pay')`。

---

## 4. 退款单 `tx_refunds.status`

状态集：`pending` 待处理 → `processing` 处理中 → `success` / `failed` / `rejected`。

| from | to | 触发 |
| --- | --- | --- |
| pending | processing | 提交渠道退款 |
| pending | rejected | 人工/规则拒绝 |
| processing | success | 渠道退款回调成功 |
| processing | failed | 渠道失败（可重新发起新退款单） |
| success | — | 终态；写渠道退款号 `channel_refund_id` |

> 幂等：创建与回调都以 `idempotency_key` / `channel_refund_id` 去重；`success` 后禁止再次同单发起（累计退款上限见对账文档）。退款成功必须同步：`tx_payments.status → refunding/refunded`、`tx_sub_orders.refund_status`、`tx_after_sales.status`，且全部在**同一事务**。

---

## 5. 售后单 `tx_after_sales.status`

状态集（tinyint）：`0` 待审核 → `1` 审核通过(待退货) → `2` 退货中 → `3` 待退款 → `4` 已完成；旁路 `5` 已拒绝、`6` 已取消。

| from | to | 触发 |
| --- | --- | --- |
| 0 | 1 | 商家审核通过（退货/换货类） |
| 0 | 5 | 审核拒绝 |
| 0 / 1 / 2 | 6 | 用户取消 / 超时未寄回 |
| 1 | 2 | 买家填退货物流 |
| 2 | 3 | 商家确认收货 / 纯退款类直接 0→3 |
| 3 | 4 | 退款回调 success（写 `refund_id`） |

> 与退款单联动：`3 → 4` 必须与 `tx_refunds.status → success` 同事务提交；`refund_id` 唯一关联。

---

## 6. 迁移守卫总表（服务层强制）

1. 所有状态更新走 `UPDATE ... SET status=?, updated_at=... WHERE id=? AND status=?`（乐观条件），失败即视为非法跃迁/并发竞争，返回错误并审计。
2. 任一迁移（尤其支付成功、退款成功、关单）成功后必须追加日志：
   - 订单：`tx_order_logs(from_status, to_status, operator, note)`
   - 支付/退款：`tx_payment_logs(action=pay/refund/refund_callback/close)`
   - 售后：`tx_after_sale_logs(action, before_status, after_status)`
3. 状态与时间轴一致性：`paid_at` 仅 paid 可写；`shipped_at` 仅 shipped 可写；`completed_at` 仅 completed 可写（PG 侧另有时间轴 CHECK，MySQL 由服务层保证）。
4. 关单/支付竞争、重复回调、部分退款、售后退款均为幂等场景：重放必须返回与首次相同的结果（见 `P0_幂等与对账口径.md`）。
